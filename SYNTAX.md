## 0. Соглашения об именах

| Как пишется | Что значит | Пример |
| --- | --- | --- |
| `m_имя` | поле класса (*member*) | `m_nodes`, `m_id1` |
| `p_имя` | параметр функции (*parameter*) | `p_fileName`, `p_id` |
| `o_имя` | выходной параметр (*output*): функция записывает в него результат | `o_count`, `o_size` |
| `ЗАГЛАВНЫЕ_БУКВЫ` | константа | `VERTICES_IN_ELEMENT` |
| `ИмяСБольшой` | тип (класс, структура) | `Mesh`, `FiniteElement` |

Компилятору эти префиксы безразличны, это договорённость для людей: по имени сразу видно,

У структур `Node` и `FiniteElement` поля без `m_`: это простые открытые наборы данных,
к их полям обращаются снаружи (`node.x`, `element.nodeIds`), и `node.m_x` читалось бы хуже.

## 1. `MeshTypes.h` — узел и конечный элемент

### 1.1. Защита от повторного включения

```cpp
#ifndef MESH_TYPES_H
#define MESH_TYPES_H
...
#endif // MESH_TYPES_H
```

Строки с `#` — команды препроцессора, они выполняются до компиляции.

Если один и тот же заголовок попадёт в `.cpp` дважды (например, напрямую и ещё раз через
другой заголовок), компилятор увидит два объявления `struct Node` и выдаст ошибку.
Эти три строки это предотвращают:

- при первом включении макрос `MESH_TYPES_H` ещё не определён, `#ifndef` («если не определён»)
  пропускает внутрь, и `#define` его определяет;
- при втором включении макрос уже есть, и всё до `#endif` выбрасывается.

Имя макроса может быть любым, принято писать имя файла заглавными буквами.
Комментарий после `#endif` — только для читателя.

### 1.2. `#include <...>` и `#include "..."`

```cpp
#include <vector>       // стандартная библиотека
#include "MeshTypes.h"  // свой файл проекта
```

`#include` буквально вставляет текст указанного файла на это место.
Угловые скобки — для стандартных заголовков, кавычки — для своих (они ищутся сначала
рядом с текущим файлом).

Что зачем подключено в `MeshTypes.h`: `<vector>` — для `std::vector`,
`<iostream>` — для `std::ostream`, `<iomanip>` — для `std::setw` и `std::setprecision`.

### 1.3. `struct`

```cpp
struct Node
{
    int id;
    double x;
    ...
};
```

`struct` — это тот же класс. Единственное отличие: у `struct` всё по умолчанию открыто
(`public`), а у `class` — закрыто (`private`). `struct` используют, когда тип —
просто набор открытых данных, как у нас.

Точка с запятой после `}` обязательна — частая ошибка.

### 1.4. Конструктор и список инициализации

```cpp
Node(int p_id, double p_x, double p_y, double p_z, bool p_isVertex = true)
    : id(p_id), x(p_x), y(p_y), z(p_z), isVertex(p_isVertex)
{}
```

`src/MeshTypes.h:22`

**Конструктор** — метод с тем же именем, что у типа, и без возвращаемого типа.
Он вызывается автоматически при создании объекта: `Node n(1, 0.0, 0.5, 1.0);`
или `Node(newId, x, y, z, false)`.

Часть после двоеточия — **список инициализации**: каждое поле сразу создаётся с нужным
значением. Тело `{}` пустое, потому что больше делать нечего.

Можно было бы написать «по-старому»:

```cpp
Node(int p_id, ...) { id = p_id; x = p_x; ... }
```

Это тоже работает, но тогда поля сначала создаются с мусором и только потом получают
значения. А константные поля и поля-ссылки так проинициализировать вообще нельзя.
Поэтому список инициализации предпочтительнее.

Поля инициализируются в том порядке, в котором объявлены в классе, а не в порядке
списка. Поэтому в списке их пишут в том же порядке, иначе компилятор выдаст предупреждение.

### 1.5. Конструктор по умолчанию

```cpp
Node()
    : id(0), x(0.0), y(0.0), z(0.0), isVertex(true)
{}
```

`src/MeshTypes.h:18`

Конструктор без параметров. Он позволяет написать просто `Node n;`.

Зачем писать его руками: если в классе объявлен хотя бы один свой конструктор, компилятор
перестаёт создавать конструктор по умолчанию сам. А без него поля `int` и `double`
остались бы с мусором.

### 1.6. Параметр по умолчанию

```cpp
bool p_isVertex = true
```

Если при вызове не передать последний аргумент, подставится `true`.
То есть `Node(1, x, y, z)` — то же самое, что `Node(1, x, y, z, true)`.
Параметры по умолчанию могут стоять только в конце списка.

### 1.7. `std::vector<int>`

```cpp
std::vector<int> nodeIds;
```

`src/MeshTypes.h:32`

`std::vector` — динамический массив из стандартной библиотеки, он сам увеличивается при
добавлении элементов. В угловых скобках — тип элементов: `vector` — это **шаблон класса**,
и `vector<int>`, `vector<Node>` — разные классы, сгенерированные по одному шаблону.

`std::` — пространство имён стандартной библиотеки, все её имена начинаются с него.

Что из `vector` используется в лабе:

| Метод | Что делает |
| --- | --- |
| `push_back(x)` | добавить элемент в конец |
| `size()` | количество элементов |
| `v[i]` | элемент по индексу (с нуля) |
| `front()`, `back()` | первый и последний элемент |
| `empty()` | пуст ли вектор |
| `reserve(n)` | заранее выделить память под `n` элементов (см. 6.4) |
| `begin()`, `end()` | итераторы на начало и конец (см. 4.5) |

### 1.8. Передача по константной ссылке

```cpp
FiniteElement(int p_id, int p_regionId, const std::vector<int>& p_nodeIds)
```

`src/MeshTypes.h:38`

- `&` — **ссылка**: функция работает с оригиналом, а не с копией. Копировать вектор дорого.
- `const` — обещание, что функция оригинал не изменит.

Правило, которому следует весь код лабы: «большие» объекты (`vector`, `string`, свои классы)
передаём как `const &`, а `int` и `double` — по значению, их копировать дешевле, чем
передавать ссылку.

Ещё одна особенность `const &`: к ней можно привязать временный объект. Поэтому
в `readHeader(file, ..., "nodes")` строковый литерал `"nodes"` сам превращается во временный
`std::string`. С обычной ссылкой `std::string&` так не получилось бы.

### 1.9. Перегрузка `operator<<`

```cpp
inline std::ostream& operator<<(std::ostream& p_out, const Node& p_node)
{
    p_out << "Node " << std::setw(5) << p_node.id << ": (" ...;
    return p_out;
}
```

`src/MeshTypes.h:45`

Здесь мы учим оператор `<<` выводить наш тип, чтобы можно было писать `std::cout << node;`.
Компилятор превращает такую запись в вызов функции `operator<<(std::cout, node)`.

- Первый параметр — поток (`std::cout`, файл и т.п.). Передаётся по обычной ссылке,
  потому что вывод меняет состояние потока.
- Второй параметр — то, что выводим, по `const &`.
- Возвращаем тот же поток по ссылке. Это нужно для цепочек: в `std::cout << a << b`
  сначала выполняется `std::cout << a`, оно возвращает `std::cout`, и к нему применяется `<< b`.

`friend` здесь не нужен: поля у `struct` открытые, функция и так может их читать.
(В лекции 2 пример с `friend` для класса `Vec3` — там поля закрытые.)

### 1.10. `inline`

Обе функции `operator<<` определены прямо в заголовке. А заголовок через цепочку `#include`
попадает в три `.cpp`-файла: `main.cpp`, `Mesh.cpp` и `MeshLoader.cpp`. Значит, тело функции
окажется скомпилировано три раза, и линковщик выдаст ошибку
`multiple definition of operator<<`.

`inline` разрешает иметь одинаковое определение функции в нескольких файлах.
Методы, написанные прямо внутри класса (как конструкторы `Node`), являются `inline`
автоматически, поэтому у них это слово не пишется.

### 1.11. Манипуляторы вывода

```cpp
p_out << std::fixed << std::setprecision(6) << std::setw(10) << p_node.x;
```

`src/MeshTypes.h:47`

| Манипулятор | Что делает |
| --- | --- |
| `std::setw(10)` | следующее значение займёт не меньше 10 символов — так получаются ровные столбцы. Действует только на одно значение |
| `std::fixed` | числа без экспоненты: `0.020000`, а не `2e-02` |
| `std::setprecision(6)` | вместе с `fixed` — 6 знаков после точки |

`fixed` и `setprecision` действуют на поток до тех пор, пока их не поменяют.
Нужен заголовок `<iomanip>`.

### 1.12. Тернарный оператор `? :`

```cpp
<< (p_node.isVertex ? "vertex" : "inner");
```

`src/MeshTypes.h:52`

Читается как «условие ? значение, если да : значение, если нет». Короткая замена `if/else`
внутри выражения.

Скобки вокруг обязательны: у `<<` приоритет выше, чем у `? :`, и без скобок компилятор
понял бы запись как `(p_out << p_node.isVertex) ? "vertex" : "inner"`.

### 1.13. Цикл с `size_t` и `++i`

```cpp
for (size_t i = 0; i < p_element.nodeIds.size(); ++i)
```

`src/MeshTypes.h:63`

`size()` возвращает беззнаковый тип `size_t`. Если взять счётчик `int i`, компилятор
предупредит о сравнении знакового числа с беззнаковым, поэтому счётчик тоже `size_t`.

`++i` или `i++` для `int` разницы нет. Префиксная форма — привычка: у сложных типов
(например, итераторов) постфиксная создаёт лишнюю временную копию.

## 2. `MeshExceptions.h` — исключения

### 2.1. `class` и `public:`

```cpp
class MeshException : public std::runtime_error
{
public:
    explicit MeshException(const std::string& p_message)
        : std::runtime_error(p_message)
    {}
};
```

`src/MeshExceptions.h:8`

У `class` всё по умолчанию закрыто. Поэтому перед конструктором стоит `public:` — иначе
создать исключение снаружи класса было бы нельзя.

### 2.2. Наследование

`: public std::runtime_error` — класс `MeshException` наследуется от стандартного класса
ошибки из `<stdexcept>`. Он получает от родителя готовое хранение текста ошибки и метод
`what()`, который этот текст возвращает.

`public`-наследование значит, что объект наследника можно использовать везде, где ожидается
родитель. Именно поэтому `catch (const MeshException&)` ловит и `FileOpenException`.

Получившаяся иерархия:

```
std::exception                стандартный базовый класс всех исключений
└── std::runtime_error        стандартная «ошибка времени выполнения»
    └── MeshException         любая ошибка загрузчика
        ├── FileOpenException     файл не открылся
        ├── FileFormatException   неверное содержимое файла
        └── BadIdException        обращение к несуществующему узлу
```

Зачем иерархия: в `main` все наши ошибки ловятся одним `catch (const MeshException&)`,
а при желании можно отдельно поймать конкретную, например только `FileOpenException`.

### 2.3. Вызов конструктора родителя

```cpp
explicit FileOpenException(const std::string& p_fileName)
    : MeshException("Can not open mesh file: " + p_fileName)
{}
```

`src/MeshExceptions.h:20`

Объект наследника содержит внутри себя «родительскую часть», и её тоже надо сконструировать.
Конструктор родителя вызывается в списке инициализации, как будто это поле.

У `std::runtime_error` нет конструктора без параметров, поэтому без этой строки код
не скомпилируется. Здесь же к тексту ошибки приклеивается понятный префикс.

### 2.4. `explicit`

Конструктор, который можно вызвать с одним аргументом, компилятор умеет использовать для
неявного преобразования типов. Без `explicit` функция, принимающая `const MeshException&`,
молча приняла бы и обычную строку — компилятор сам сделал бы из неё исключение.

`explicit` это запрещает: объект можно создать только явно — `MeshException("текст")`.

### 2.5. Склейка строк и `\"`

```cpp
"Can not open mesh file: " + p_fileName
```

`+` склеивает строки, если хотя бы одна из частей — `std::string`. Два строковых литерала
сложить нельзя: `"a" + "b"` — ошибка, потому что литералы — это указатели на символы.

`\"` — кавычка внутри строки (`src/MeshLoader.cpp:12`). Обратная косая черта говорит, что эта
кавычка — символ строки, а не её конец.

## 3. `Mesh.h` — объявление класса сетки

### 3.1. Объявление в `.h`, определение в `.cpp`

В `Mesh.h` написано только, **что** есть у класса: поля, какие методы, какие у них параметры
и что они возвращают. **Как** методы работают — их тела — написано в `Mesh.cpp`.

Так делают потому, что компилятор собирает каждый `.cpp` отдельно, и другим файлам
(например, `main.cpp`) для вызова метода достаточно знать его объявление.

Исключение — очень короткие методы, написанные прямо в классе, например конструктор
`HasThreeNodes` (`src/Mesh.h:16`). Они автоматически становятся `inline`.

### 3.2. `public:` и `private:`

```cpp
class Mesh
{
public:
    // методы, доступные всем
private:
    // поля и вспомогательные методы, доступные только самому классу
    std::vector<Node> m_nodes;
    ...
};
```

`src/Mesh.h:32`, `src/Mesh.h:72`

Всё, что после `private:`, могут использовать только методы самого `Mesh`. Снаружи нельзя,
например, удалить из `m_nodes` узел, на который ещё ссылаются элементы, и тем самым
сломать сетку. Получить данные можно только через открытые методы. Это и есть
**инкапсуляция**.

### 3.3. Функтор-предикат `HasThreeNodes`

```cpp
class HasThreeNodes
{
public:
    HasThreeNodes(int p_id1, int p_id2, int p_id3)
        : m_id1(p_id1), m_id2(p_id2), m_id3(p_id3)
    {}

    bool operator()(const FiniteElement& p_element) const;

private:
    int m_id1;
    int m_id2;
    int m_id3;
};
```

`src/Mesh.h:13`

Класс с перегруженным оператором `()` называется **функтором**: его объект можно «вызвать»
как функцию — `predicate(element)`. Если функтор возвращает `bool`, он называется
**предикатом**. Задание прямо требовало создать предикат для алгоритма `find_if`.

В записи `bool operator()(const FiniteElement& p_element) const` первые `()` — часть имени
метода, вторые — его список параметров.

Почему не обычная функция: `find_if` передаёт предикату ровно один аргумент — проверяемый
элемент. А нам для проверки нужны ещё три номера узлов. Функтор получает их в конструкторе
и хранит в полях: «запомнил при создании — использовал при вызове».

### 3.4. `const` после метода

```cpp
const std::vector<Node>& getNodes() const;
```

`src/Mesh.h:39`

Последнее `const` означает: метод не меняет поля объекта. Если внутри такого метода
попытаться изменить поле, будет ошибка компиляции.

Такие методы можно вызывать у константного объекта и через `const`-ссылку. У `Mesh`
почти все методы константные. Не константные только `splitEdges` и `addMiddleNodes` —
они действительно меняют сетку.

### 3.5. Возврат константной ссылки

```cpp
const std::vector<Node>& getNodes() const;
```

Метод отдаёт ссылку на поле `m_nodes`, а не его копию. Для 85 узлов это неважно, но реальные
сетки бывают по миллиону узлов.

`const` в начале запрещает менять вектор через эту ссылку: `mesh.getNodes().push_back(...)`
не скомпилируется. Читать можно, портить нельзя.

### 3.6. Вектор векторов и пробел в `> >`

```cpp
std::vector<std::vector<int> > getNodeNeighbours() const;
```

`src/Mesh.h:63`

Вектор, каждый элемент которого — вектор `int`. Похоже на двумерный массив, но строки
могут быть разной длины: у каждого узла своё число соседей.

Пробел между `> >` — привычка старого C++: до стандарта C++11 запись `>>` считалась оператором
сдвига, и код не компилировался. Начиная с C++11 можно писать слитно `>>`.

### 3.7. `std::pair` и `std::map`

```cpp
std::vector<std::pair<int, int> > makeEdges(int p_vertexCount);
std::map<std::pair<int, int>, int>& p_createdNodes
```

`src/Mesh.h:78`, `src/Mesh.h:85`

`std::pair<int, int>` — пара значений, поля называются `.first` и `.second`.
Ребро удобно хранить как пару номеров его узлов.

`std::map<Ключ, Значение>` — словарь. Здесь ключ — ребро (пара номеров узлов), значение —
номер узла, созданного в середине этого ребра. Поиск по ключу работает за O(log n).
Ключи хранятся отсортированными; пары сравниваются сначала по `first`, потом по `second`.

Заголовки: `<utility>` для `pair`, `<map>` для `map`.

### 3.8. `static`-метод

```cpp
static std::vector<std::pair<int, int> > makeEdges(int p_vertexCount);
```

`src/Mesh.h:78`

Статический метод не привязан к конкретному объекту: ему не передаётся `this`, и обращаться

### 4.5. Итераторы

**Итератор** — объект, который указывает на элемент контейнера, примерно как указатель:

| Запись | Что значит |
| --- | --- |
| `*it` | сам элемент |
| `it->id` | поле элемента |
| `++it` | перейти к следующему элементу |
| `v.begin()` | итератор на первый элемент |
| `v.end()` | итератор на позицию **после** последнего элемента |

`end()` указывает не на последний элемент, а за него. Все алгоритмы STL принимают пару
итераторов «начало, конец» и обрабатывают всё от начала до конца, не включая конец.

`const_iterator` — итератор только для чтения. В константном методе `begin()` у поля
возвращает именно `const_iterator`, поэтому переменная объявлена с этим типом
(`src/Mesh.cpp:73`).

### 4.6. `std::find`

```cpp
return std::find(nodes.begin(), nodes.end(), m_id1) != nodes.end()
    && std::find(nodes.begin(), nodes.end(), m_id2) != nodes.end()
    && std::find(nodes.begin(), nodes.end(), m_id3) != nodes.end();
```

`src/Mesh.cpp:15`

`std::find` (из `<algorithm>`) ищет значение в диапазоне. Возвращает итератор на найденный
элемент, а если ничего не нашёл — `end()`. Поэтому `!= nodes.end()` читается как «найдено».

`&&` проверяется слева направо и останавливается на первом `false`: если первый узел
не найден, остальные два даже не ищутся.

Строкой выше `const std::vector<int>& nodes = p_element.nodeIds;` — локальная ссылка,
просто короткое второе имя для `p_element.nodeIds`. Копии при этом нет.

### 4.7. `std::find_if` — найти все подходящие элементы

```cpp
HasThreeNodes predicate(p_id1, p_id2, p_id3);
std::vector<FiniteElement>::const_iterator it = m_elements.begin();

while ((it = std::find_if(it, m_elements.end(), predicate)) != m_elements.end())
{
    result.push_back(it->id);
    ++it;
}
```

`src/Mesh.cpp:69`

`std::find_if` — как `find`, только вместо значения принимает предикат. Возвращает первый
элемент, для которого `predicate(элемент)` вернул `true`.

`find_if` находит только **первый** подходящий элемент, а нам нужны все. Поэтому цикл:

1. ищем, начиная с позиции `it`;
2. результат сразу записываем обратно в `it` — это присваивание внутри условия `while`.
   Внешние скобки вокруг присваивания обязательны: без них из-за приоритетов сначала
   выполнилось бы `!=`;
3. если `it` не равен `end()`, элемент найден: запоминаем его `id` и сдвигаемся на один
   вперёд. Без `++it` следующий поиск снова нашёл бы этот же элемент — вечный цикл;
4. повторяем поиск с новой позиции, пока не дойдём до конца.

Каждый элемент просматривается один раз, сложность O(n).

### 4.8. Лямбда-функции и `std::for_each`

```cpp

    [&](const FiniteElement& p_element)
    {
        if (p_element.regionId == p_regionId)
            result.push_back(p_element.id);
    });
```

`src/Mesh.cpp:107`

`std::for_each` вызывает переданную функцию для каждого элемента диапазона. По сути это тот же
цикл `for`, но через алгоритм STL — задание требовало свести циклы к минимуму.

Третий аргумент — **лямбда**: безымянная функция, написанная прямо на месте использования.
Общий вид:

```
[захват](параметры) { тело }
```

Компилятор превращает лямбду в класс-функтор с `operator()` — то же самое, что
`HasThreeNodes`, только записанное короче.

### 4.9. Захват: `[&]` и `[]`

Лямбда — отдельная функция, и по умолчанию она не видит локальные переменные вокруг себя.
Квадратные скобки говорят, какие переменные ей дать:

| Захват | Что значит | Где в лабе |
| --- | --- | --- |
| `[&]` | все внешние переменные по ссылке: лямбда может их читать и менять, изменения видны снаружи | почти везде: лямбда читает `p_regionId` и добавляет в `result` |
| `[]` | ничего не захватывать | `src/Mesh.cpp:199`: лямбде нужен только её параметр |
| `[=]` | копии всех внешних переменных | в лабе не используется |

`[&]` захватывает и `this`, поэтому внутри лямбды доступны поля и методы класса.
Так в `addMiddleNodes` лямбда вызывает `getNode` и дописывает в `m_nodes`.

Внутри константного метода через `this` менять поля нельзя, а свои локальные переменные
(`result`, `neighbours`) — можно. Поэтому методы поиска остаются `const`.

### 4.13. `std::transform`

### 4.14. Вложенный цикл, `make_pair`, `min` и `max`


`std::make_pair(i, j)` создаёт `pair`, не выписывая его тип.

```cpp

                                         std::max(first, second));
```

`src/Mesh.cpp:226`

`std::min` и `std::max` (из `<algorithm>`) — меньшее и большее из двух чисел. Ключ ребра всегда
записывается как «меньший номер, больший номер». Тогда ребро 13–14 одного тетраэдра и ребро

### 4.15. `map`: поиск и вставка

```cpp
std::map<std::pair<int, int>, int>::const_iterator found = p_createdNodes.find(key);

if (found == p_createdNodes.end())
{
    ... создаём новый узел ...
    found = p_createdNodes.insert(std::make_pair(key, newId)).first;
}

```

`src/Mesh.cpp:229`

- `map::find(key)` возвращает итератор на найденную запись или `end()`, если ключа нет.
- Каждая запись в `map` — это `pair`: `found->first` — ключ (ребро),
  `found->second` — значение (номер узла).
- `insert` возвращает пару «итератор на вставленную запись, вставлено ли (`bool`)».

только что. Поэтому последняя строка одна на оба случая.

### 4.16. Неконстантная ссылка в параметре и в лямбде

```cpp
    [&](FiniteElement& p_element)
```

### 4.17. Почему `Node a` — копия, а не ссылка

```cpp
Node a = getNode(first);
Node b = getNode(second);
...
m_nodes.push_back(Node(newId, ...));
```

`src/Mesh.cpp:237`

`getNode` возвращает ссылку на элемент внутри `m_nodes`. Но `push_back` может не уместиться
в уже выделенной памяти. Тогда `vector` выделяет новый кусок памяти, переносит туда все
элементы, а старый освобождает — и все ссылки на старые элементы начинают указывать
в никуда. Это классическая ловушка `vector`.

Чтобы не разбираться, в какой момент ссылка ещё жива, координаты просто копируются.
`Node` — маленькая структура, копировать её дёшево.

## 5. `MeshLoader.h` — загрузчики

### 5.1. Чисто виртуальный метод и абстрактный класс

```cpp
class MeshLoader
{
public:
    virtual ~MeshLoader() {}
    virtual Mesh loadMesh(const std::string& p_fileName) = 0;
};
```

`src/MeshLoader.h:13`

- `virtual` — метод можно переопределить в наследнике. Если вызвать его через указатель
  или ссылку на базовый класс, выполнится версия наследника. Это **позднее связывание**:
  какую версию вызвать, решается во время работы программы.
- `= 0` — **чисто виртуальный** метод: у базового класса реализации нет вообще.

Класс, в котором есть хотя бы один чисто виртуальный метод, — **абстрактный**. Создать его
объект нельзя: `MeshLoader loader;` — ошибка компиляции. От него можно только наследоваться.
`MeshLoader` — это «контракт»: любой загрузчик обязан уметь `loadMesh`.

Пример, где это пригождается (в коде лабы его нет):

```cpp
MeshLoader* loader = new AneuMeshLoader;   // завтра здесь может быть другой загрузчик
Mesh mesh = loader->loadMesh(fileName);    // вызовется метод AneuMeshLoader
delete loader;
```

Код, который использует загрузчик через `MeshLoader*`, не меняется, когда добавляется
новый формат файла. Именно этого задание и просило.

### 5.2. Виртуальный деструктор

```cpp
virtual ~MeshLoader() {}
```

`src/MeshLoader.h:16`

В примере выше `delete loader` удаляет объект через указатель на базовый класс.
Без `virtual` у деструктора вызвался бы только деструктор `MeshLoader`, а деструктор
наследника — нет. Правило: если в классе есть виртуальные методы, деструктор тоже делают
виртуальным.

### 5.3. `override`

```cpp
class AneuMeshLoader : public MeshLoader
{
public:
    Mesh loadMesh(const std::string& p_fileName) override;
```

`src/MeshLoader.h:27`

`override` говорит: «этот метод переопределяет виртуальный метод базового класса».
Компилятор это проверит. Если ошибиться в объявлении (например, написать `std::string`
вместо `const std::string&`), будет ошибка компиляции. Без `override` компилятор молча
создал бы новый, отдельный метод, и переопределение просто не сработало бы.

### 5.4. Выходные параметры

```cpp

                const std::string& p_blockName);
```

`src/MeshLoader.h:32`

Если чтение не удалось (в файле буквы вместо числа или файл закончился раньше времени),

Ошибку самого чтения поймает проверка `if (!p_file)` чуть ниже.

### 6.4. `reserve(n)` и `vector(n)`

| Запись | Размер после | Зачем |
| --- | --- | --- |
| `v.reserve(n)` | 0 | заранее выделить память под `n` элементов. Элементы потом добавляются через `push_back`, и вектору не придётся перевыделять память — быстрее. Количество узлов известно из заголовка файла |
| `std::vector<int> v(n)` | `n` (нули) | сразу получить `n` элементов, чтобы писать по индексу: `nodeIds[j]` |

Проще запомнить: `reserve` даёт место, `vector(n)` даёт элементы.

### 6.5. Возврат объекта по значению

```cpp
return Mesh(nodes, elements, boundaryElements);
```

`src/MeshLoader.cpp:123`

`loadMesh` возвращает `Mesh` по значению — так требует задание. Лишнего копирования объекта
при возврате нет: компилятор сразу создаёт его в переменной `mesh` в `main`. Эта оптимизация
называется **copy elision** (RVO).

Для честности: векторы `nodes`, `elements`, `boundaryElements` при этом один раз копируются
в поля `Mesh`, потому что конструктор принимает их по `const &`. Убрать эту копию можно
семантикой перемещения (`std::move`), но в лабе она не используется, чтобы не усложнять код.

### 7.3. `try` / `catch`

```cpp

{
    AneuMeshLoader loader;
    Mesh mesh = loader.loadMesh(argv[1]);
    ...
}
catch (const MeshException& e)
{
    std::cerr << "Mesh error: " << e.what() << std::endl;
    return 1;
}
catch (const std::exception& e)
{
    std::cerr << "Error: " << e.what() << std::endl;
    return 1;
}
```

`src/main.cpp:28`, `src/main.cpp:95`

Если где-то внутри `try` — даже глубоко, в `loadMesh` → `readElements` — выполнился `throw`,
остаток блока `try` пропускается и выполняется первый подходящий `catch`.
Бросили `FileOpenException` — подходит `catch (const MeshException&)`, потому что
`FileOpenException` — его наследник.

**Порядок `catch` важен.** Они проверяются сверху вниз. Наши исключения тоже являются
наследниками `std::exception`. Если поставить `catch (const std::exception&)` первым,
он перехватывал бы вообще всё, и `catch` для `MeshException` никогда бы не сработал.
Правило: обработчики наследников пишутся выше обработчиков родителей.

Второй `catch` — страховка на случай стандартных ошибок, например `std::bad_alloc`
(не хватило памяти).

Ловим по `const &`, чтобы не копировать объект исключения и не получить «срезку»: при
перехвате по значению базового типа скопировалась бы только базовая часть объекта.

### 7.4. `what()`

`e.what()` — виртуальный метод `std::exception`, он возвращает текст ошибки. Сами мы его
не писали: текст был передан в конструктор `std::runtime_error` (см. 2.3), и тот его хранит
и возвращает. Так как `catch` ловит по ссылке, а `what()` виртуальный, всё работает для
любого наследника.

## 8. `Makefile` — сборка

`Makefile` — не C++, а инструкции для программы `make`: как собрать проект.

```make
CXX = g++
CXXFLAGS = -std=c++11 -Wall -Wextra -O2
SOURCES = src/main.cpp src/Mesh.cpp src/MeshLoader.cpp
OBJECTS = $(SOURCES:.cpp=.o)
```

Это переменные. Значение подставляется записью `$(ИМЯ)`.
`$(SOURCES:.cpp=.o)` — список из `SOURCES`, в котором `.cpp` заменено на `.o`.

Флаги компилятора:

| Флаг | Что значит |
| --- | --- |
| `-std=c++11` | компилировать по стандарту C++11 |
| `-Wall -Wextra` | включить почти все предупреждения |
| `-O2` | оптимизировать код |
| `-c` | только скомпилировать в `.o`, без сборки программы |
| `-o имя` | как назвать результат |

```make
$(TARGET): $(OBJECTS)
	$(CXX) $(CXXFLAGS) -o $@ $(OBJECTS)

%.o: %.cpp
	$(CXX) $(CXXFLAGS) -c $< -o $@
```

Правило записывается как `цель: от чего зависит`, а на следующей строке — команда.
**Команда обязательно начинается с табуляции, а не с пробелов**, иначе `make` выдаст ошибку.

- `%.o: %.cpp` — общее правило «любой `.o` собирается из одноимённого `.cpp`»;
- `$@` — цель правила (например, `src/Mesh.o`);
- `$<` — первая зависимость (например, `src/Mesh.cpp`).

`make` пересобирает только те файлы, которые изменились с прошлой сборки.

`.PHONY: all run clean` — эти цели не являются файлами, это просто имена команд.
Вызываются как `make run` и `make clean`. Просто `make` выполняет первую цель — `all`.
